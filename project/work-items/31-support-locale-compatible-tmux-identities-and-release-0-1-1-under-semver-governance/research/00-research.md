# Research Brief: Support locale-compatible tmux identities and release 0.1.1 under SemVer governance

## GitHub Issue
- **Issue:** #31
- **Title:** Support locale-compatible tmux identities and release 0.1.1 under SemVer governance
- **Work Item:** `project/work-items/31-support-locale-compatible-tmux-identities-and-release-0-1-1-under-semver-governance`

## Scope Classification
- **Scope Type:** issue

## Problem Statement

The published 0.1.0 behavior assumes that horizontal tab bytes survive formatted tmux command output. The reported production-like Doctor run instead completed `window-create` with zero exit and a complete six-byte LF-terminated stdout record containing no horizontal tab, so the strict identity parser classified the result as malformed before validating the returned IDs. Repository and upstream tmux 3.7b evidence show that the command clients run without a UTF-8 client flag and that tmux sanitizes control bytes for such clients, which explains the observed shape. The same transport is used by normal issue-window creation and observation and by the isolated Doctor probe.

The correction is bounded by the exact ownership, cwd, no-adoption, one-pass retry, value-free diagnostic, and unconditional Doctor cleanup contracts accepted for Issue #29. Issue #31 also requires the backward-compatible package correction to move the current release from 0.1.0 to 0.1.1 and requires explicit Semantic Versioning governance without expanding the product into a service, API, or broader release system.

- Authoritative tmux 3.7b source confirms the causal chain. `tmux.c` sets `CLIENT_UTF8` for `-u`, inherited `TMUX`, or locale text containing UTF-8/UTF8, none of which the current Runner command environments supply ([tmux.c lines 460-503](https://github.com/tmux/tmux/blob/3.7b/tmux.c#L460-L503)). `cmd_new_window_exec` formats `-F` output and calls `cmdq_print` ([cmd-new-window.c lines 153-158](https://github.com/tmux/tmux/blob/3.7b/cmd-new-window.c#L153-L158)); `cmdq_print` calls `cmdq_print_data`, which calls `server_client_print` ([cmd-queue.c lines 835-857](https://github.com/tmux/tmux/blob/3.7b/cmd-queue.c#L835-L857)). For a command client without `CLIENT_UTF8`, `server_client_print` calls `utf8_sanitize` before appending LF ([server-client.c lines 2801-2840](https://github.com/tmux/tmux/blob/3.7b/server-client.c#L2801-L2840)). `utf8_sanitize` maps every byte at or below `0x1f`, including HT `0x09`, to underscore ([utf8.c lines 778-814](https://github.com/tmux/tmux/blob/3.7b/utf8.c#L778-L814)). This predicts one printable replacement for the separator plus the separately appended LF, matching the reported byte count, field count, and value-free signature without reconstructing raw identity values.
- The tmux 3.7b manual independently documents that `-u` writes UTF-8 output when the first set locale variable does not name UTF-8 ([tmux.1 lines 216-226](https://github.com/tmux/tmux/blob/3.7b/tmux.1#L216-L226)) and that non-UTF8 output is restricted and replaced with underscores ([tmux.1 lines 8319-8333](https://github.com/tmux/tmux/blob/3.7b/tmux.1#L8319-L8333)). The present failure is therefore client-state dependent, not evidence that tmux 3.7b failed to format identities.

## Constraints

- The accepted Issue #29 architecture currently permits HT as the only field separator and explicitly prohibits alternate separators in `ADR-260814-tmux-identity-failure-recovery` and `CORE-COMPONENT-260814-tmux-identity-diagnostics`. Issue #31 requires compatibility across both client states while retaining a finite closed accepted set. Research records this contract conflict without selecting a transport or changing architecture.
- Creation must still prove exactly one complete strict window ID and pane ID. Observation must prove those exact IDs plus one nonempty valid UTF-8 cwd equal to the expected cwd. Partial, extra, empty, multi-record, invalid-terminator, and unsupported-separator output remains malformed.
- The identity parser and diagnostic builder operate on original bytes before decoding. Raw output, identities, cwd/path, arguments, environment, commands, hashes, byte values, secrets, and unrelated-run values cannot enter errors, snapshots, events, reports, logs, Doctor evidence, or rendering.
- Identity evidence and diagnostics never authorize ownership or retry. Existing lock, lease, worktree path/registration/branch, fetched-base HEAD, staged/unstaged/untracked cleanliness, no persisted identity, zero same-name candidates, immediate name-absence recheck, and single creation-attempt bounds remain authoritative. Same-name resources remain unproved and preserved.
- Reconciliation remains one bounded observation per external boundary with no polling, hidden retry, or second collection after persisting a malformed observation diagnostic. Nonzero observation remains absence; malformed zero-exit observation remains unknown.
- Doctor must retain exactly 24 ordered blocking checks and keep `command.tmux` as the complete isolated functional readiness row. Every success, failure, timeout, cancellation, and deadline path must settle exact managed server/helper/socket/workspace cleanup before returning; cleanup uncertainty overrides functional success.
- Normal subprocesses remain shell-free typed executable/argument arrays under the existing finite environment allowlist and 15-second tmux bounds. Doctor remains private-socket, empty-configuration, credential-free, shell-free, capped at 4096 retained bytes per stream, 2 seconds per command/wait, and 9 seconds aggregate.
- Repository-controlled validation cannot inherit ambient locale or tmux state and cannot access credentials, network services, Sparkta, default tmux, or unowned resources. Distinct overlapping flows cannot infer ownership from names or share identities/cwd accidentally.
- The release number must agree across the finite product surfaces, while unrelated dependency versions containing 0.1.0 in `package-lock.json` remain dependency metadata. - The package remains the npm-distributed strict TypeScript Node.js CLI selected by `ADR-260810-typescript-node-cli`. No current evidence requires a network API, service, daemon, database, container, protocol change, or destructive data migration.
- The new `AGENTS.md` governance requirement must use the existing APS instruction structure. The APS v1.2.2 badge rule is independent of the Runner package release and changes only if the APS skill is upgraded.

## Risks and Open Questions

- The accepted HT-only architecture and the new two-client-state acceptance criteria conflict. The finite accepted transport forms are not yet stated in repository architecture or code, and Research does not resolve them.
- Existing valid fake tmux fixtures emit HT regardless of the environment supplied by production code. They therefore mask the upstream non-UTF8 sanitization path and do not prove that current production environment facts correspond to their output.
- The incident supplies structural facts only. Upstream source explains the replacement class, but raw stdout must remain unavailable; later work cannot rely on a leaked identity or path value as proof.
- Printable substitution can make a separator indistinguishable from ordinary printable data unless the accepted grammar remains finite and unambiguous across identifier and cwd fields. Unsupported printable and control separators must not gain accidental acceptance.
- Current normal concurrency tests prove resource disjointness but not overlapping identity transport, and current Doctor isolation tests prove one probe at a time. Cross-owned return values or cleanup facts under overlap are not presently covered.
- The tracked product-version inventory is small, but broad replacement of every 0.1.0 in `package-lock.json` would alter unrelated dependency metadata. Product release values must remain distinguishable from dependency versions and ranges.
- Packed tests install real tarballs but do not currently assert all packed, installed, generated-manifest, and clean-install release identities. A stale hardcoded fixture or catalog constant can agree locally while packed metadata remains unexamined.
- The CLI has no `--version` command, README has no current-version or upgrade procedure, and the issue does not identify an npm registry publication step. The exact user-facing confirmation surface and whether release means repository metadata/package proof or external publication remain unresolved by current repository evidence.
- SemVer item 6 formally scopes the patch rule to `x > 0`, while item 4 calls 0.y.z unstable. Issue #31 explicitly requires 0.1.1, but a durable general rule for correct major/minor/patch treatment during pre-1.0 development needs unambiguous wording.
- No Research-stage blocker remains. The unresolved transport, governance wording, and release-confirmation questions belong to later RPIV stages; they do not justify broader product scope or access to external consumer state.
