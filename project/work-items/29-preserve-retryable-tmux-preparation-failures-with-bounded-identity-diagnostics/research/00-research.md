# Research Brief: Preserve retryable tmux preparation failures with bounded identity diagnostics

## Scope Classification
- **Scope Type:** issue

## Problem Statement

Issue #29 began with a retained `starting_tmux` run whose malformed tmux identity output could not be reconstructed safely. Commit `84f5cbe138f8e1653624d6a1c8750e2ccceb1036` now contains the prior AC-1 through AC-9 identity parsing, bounded diagnostics, persistence, and recovery behavior. The updated issue adds a repository-readiness gap: product Doctor currently treats an executable tmux path as ready even though Runner depends on a working tmux server and specific session, window, pane, identity-format, observation, and cleanup behavior.

The remaining research boundary is to characterize current Doctor and tmux contracts without selecting a design. Any decision to strengthen an existing Doctor check or introduce a different check belongs to Plan. The unavailable external incident bytes remain insufficient to infer a tmux-version defect or alternate separator, and the external Sparkta state remains outside the research boundary.

## Acceptance Criteria

<!-- ACCEPTANCE_CRITERIA_START -->
- [ ] Creation accepts exactly one nonempty record with exactly two fields representing one `^@[0-9]+$` window ID and one `^%[0-9]+$` pane ID; observation accepts exactly one nonempty record with exactly three fields representing those two IDs and one nonempty cwd. The accepted transport permits only the documented record terminator and field separator, including an optional final line terminator, and rejects additional records or fields.
- [ ] Controlled tmux 3.7b fixtures with creation bytes `40 31 09 25 31 0a` and observation bytes `40 31 09 25 31 09 2f 74 6d 70 0a` produce the exact identities `@1`, `%1`, and `/tmp` and preserve the existing successful preparation/reconciliation behavior.
- [ ] The bounded malformed matrix rejects creation outputs `empty`, `@1\n`, `@1<TAB>%1<TAB>extra\n`, `@1<TAB>%1\n@2<TAB>%2\n`, `1<TAB>%1\n`, and `@1<TAB>1\n`; it also rejects observation outputs `empty`, `@1<TAB>%1\n`, `@1<TAB>%1<TAB>/tmp<TAB>extra\n`, `@1<TAB>%1<TAB>/tmp\n@2<TAB>%2<TAB>/tmp\n`, `1<TAB>%1<TAB>/tmp\n`, and `@1<TAB>1<TAB>/tmp\n`. Each case reports malformed or ambiguous identity output rather than accepting a partial record.
- [ ] A creation or observation identity failure exposes a retained structural diagnostic through the next repository-owned JSON status or reconciliation result: command phase (`create` or `observe`), exit code, stdout/stderr byte counts, record count capped at 8 with a truncation flag, per-record field counts capped at 8 with truncation flags, and a structural token signature capped at 32 tokens that distinguishes IDs, horizontal tabs, CR/LF, backslashes, and other byte runs without retaining their values.
- [ ] Retained identity diagnostics never contain raw stdout or stderr, cwd/path components, command arguments, environment values, field values, issue/owner/run identifiers, or bytes from an `other` run; human output identifies malformed or ambiguous tmux identity evidence and does not recommend upgrading a tmux version already demonstrated to emit the supported format.
- [ ] After a failed creation parse with no remaining same-name tmux window, a `starting_tmux` fixture whose lock, lease, branch, worktree path/registration/HEAD/cleanliness still match can resume with exactly one new window-creation attempt and then continue the existing preparation transition when valid identity output is returned; lock, lease, branch, worktree, window, worker, and RPIV-launch call counts prove that no duplicate owned resources are created.
- [ ] If any same-name tmux window is present while the snapshot has no persisted tmux identity, resume keeps the existing unknown-ownership refusal and leaves snapshot ownership fields, lock, lease, Git worktree tuple, tmux inventory, worker processes, and RPIV launches unchanged; the change does not infer or adopt ownership from a name, cwd, or process command.
- [ ] `LOG_NOT_FOUND` remains a bounded logs outcome when no persisted tmux identity/transcript exists and does not change reconciliation: matching preparation ownership authorizes only `PREPARATION_RESUME_AVAILABLE` and its existing `resume` action, while mismatched or unknown ownership still authorizes no resume.
- [ ] Credential-free tests use temporary repositories and controlled command/tmux/process adapters or executables, never access the external consumer repository, and pass through the existing `just verify-focused` and `just verify` recipes.
- [ ] `soft-factory doctor --json` reports tmux ready only after a bounded functional probe on a uniquely isolated tmux server proves the session/window/pane operations and exact identity/observation formats Runner requires; an installed but nonfunctional or malformed tmux fails readiness with structured actionable evidence, while success and failure both leave ambient tmux servers untouched and no probe session, window, pane, process, socket, or temporary file behind.

- `src/doctor.ts` `DOCTOR_CHECK_IDS` is a closed, exact 24-check order: `repository.git-membership`, `repository.primary-worktree`, `repository.git-common-directory`, `repository.github-identity`, `repository.default-branch`, `command.git`, `command.gh`, `command.tmux`, `command.node`, `command.copilot`, `authentication.github-cli`, `authentication.copilot-cli`, `compatibility.rpiv-agent`, `compatibility.runner-protocol`, `compatibility.configuration`, `compatibility.worktree-root`, `compatibility.state-root-writable`, `compatibility.trees-ignored`, `compatibility.runtime-state-ignored`, `compatibility.result-contract`, `runtime.trees-ownership`, `runtime.state-readable`, `runtime.locks-interpretable`, and `runtime.required-paths-creatable`.
- `src/doctor.ts` `DoctorResultV1` is schema version 1 with `ready`, nullable repository facts, and exactly those ordered checks. Every check is blocking and is only `passed` or `failed`; failed entries add nonempty `message` and `remediation`, while passed entries carry no evidence fields. `makeDoctorResult` rejects a missing, additional, or reordered check and computes ready as the conjunction of all 24 statuses.
- `src/doctor-service.ts` `DoctorService.evaluate` resolves executables first, observes repository facts, runs authentication and compatibility concurrently, then runs runtime inventory, maps observations to the fixed IDs, and renders one result. Executable observations are the only tmux input: no compatibility or runtime layer currently receives a tmux executable or performs a tmux command.
- Current `command.tmux` semantics are executable presence only. `src/doctor-adapters.ts` `resolveDoctorExecutables` searches PATH for a regular file with execute permission; `DoctorService` assigns `executables.tmux` directly to `command.tmux`. The Doctor guide, README, ready/blocked manifests, `src/doctor.test.ts`, `src/asset-doctor-regression.test.ts`, and documentation assertions all describe or enforce this meaning.
- `src/doctor-adapters.ts` defines a Doctor-specific `DoctorCommandRunner`. Each spec is shell-free, has an exact `timeoutMs: 2000`, and receives only the allowlisted `PATH`, `HOME`, `XDG_CONFIG_HOME`, `GH_CONFIG_DIR`, `TMPDIR`, and `NODE_EXTRA_CA_CERTS` entries. The live runner captures exit code, signal, decoded stdout/stderr, timeout, and launch error; timeout sends SIGTERM and schedules SIGKILL after 100 ms.
- Doctor command redaction replaces recognized GitHub token forms and token/password/secret assignments, then truncates each returned stream to 4096 characters; failure detail is further truncated to 240 characters. The runner accumulates all process output buffers before decoding and truncating, and `DoctorCommandResult` has no original byte buffers, byte counts, process identity, or cleanup handle. This differs from `src/live.ts` `CommandResult`, which now carries original buffers and byte counts for tmux identity parsing.
- `src/doctor-service.ts` races evaluation against a 9000 ms aggregate timer and converts timeout or uncaught adapter failure into a complete all-failed 24-check result. The timer does not cancel `evaluate`. `LiveDoctorCommandRunner` waits for client close after signals. There is currently no Doctor tmux server lifecycle or post-timeout resource observation.
- Production Doctor has no temporary-directory abstraction and does not call `fs.mkdtemp` or `os.tmpdir`. `src/doctor-compatibility.ts` creates one exclusive `.doctor-write-<token>` file under the validated state root and may create/remove that root. `src/doctor-runtime.ts` creates exclusive `.doctor-path-<label>-<token>` files under nearest validated repository-contained ancestors. Both track only exact resources they created, attempt cleanup in failure paths, and report cleanup uncertainty as a failed observation.
- Tests do use temporary directories: Doctor adapter, compatibility, runtime, and integration suites call `fs.mkdtemp(path.join(os.tmpdir(), ...))` and remove fixture roots recursively. `DoctorServiceInput` exposes an injected command runner, PATH value, and deterministic token; `runCli` accepts an injected `DoctorRunner`; issue ports are guarded by tripwires.
- The current built ready fixture in `src/doctor-integration.test.ts` installs a fake tmux executable containing only `process.exitCode=0;`. The controlled service runner has no tmux branch. Therefore the existing 24-row matrix proves `command.tmux` presence/absence only and supplies no functional session, window, pane, format, observation, startup, or cleanup proof.
- The committed Runner tmux adapter in `src/live.ts` depends on `has-session`; detached `new-session`; name-formatted `list-windows`; detached print-formatted `new-window`; identity/cwd-formatted `list-panes`; `display-message` for pane PID; `set-window-option remain-on-exit`; `capture-pane`; `respawn-pane -k`; `kill-window`; and interactive `select-window`, `select-pane`, and `attach-session`. Every bounded noninteractive Runner tmux call uses 15000 ms and hardcodes `tmux` without a global socket selector.
- `src/ports.ts` `TmuxPort` exposes creation, same-name observation, exact identity observation, pane PID, remain-on-exit, capture, respawn, window removal, and attach. `LiveTmuxPort` is private to `src/live.ts`; `createLivePorts` permits a controlled `CommandRunner`, but the production adapter targets the normal tmux server and its Runner operations are not directly configurable for an isolated Doctor server.
- The upstream tmux 3.7b manual documents two selectors that avoid the default socket: global `-L socket-name` permits independent servers under `TMUX_TMPDIR` or `/tmp/tmux-UID`, and global `-S socket-path` uses a full alternative path, bypasses the default socket directory, and overrides `-L`. It also documents that `new-session` creates a session, `kill-server` destroys the selected server and all its sessions, and server startup loads system and user configuration unless an alternate configuration file is selected. These are external command semantics; no live isolation probe was executed.
- `doctorEnvironment` does not pass inherited `TMUX` or `TMUX_TMPDIR`, but omitting `TMUX` alone does not distinguish a probe from the default `/tmp/tmux-UID/default` server. It does pass `HOME` and `XDG_CONFIG_HOME`, so a newly started server can observe ambient tmux configuration under the default startup rules documented by tmux 3.7b.
- Current startup and cleanup boundaries are filesystem-only. A tmux client command can start a separate server process, while the Doctor runner observes and signals only its direct client child. The repository has no existing fact that proves a server process, socket, session, window, pane, or pane child is absent after success, command failure, parse failure, timeout, aggregate timeout, or cleanup-command failure.
- `src/doctor-render.ts` renders both JSON and human output from `DoctorResultV1`; `src/index.ts` exits 0 only for ready and 3 for a complete not-ready report. Human output prints every check plus failure message/remediation. There is no separate structured evidence object for tmux probe phase, operation, cleanup, or failure classification.

## Constraints

- Accepted Doctor architecture requires exactly 24 ordered blocking IDs, schema-v1 human/JSON parity, readiness only when every check passes, complete failed results rather than fail-fast omission, exit 0/3 behavior, 2-second external-call bounds, a 9-second aggregate deadline, one attempt, and no hidden retry or polling (`ADR-260812-repository-doctor-readiness`; `CORE-COMPONENT-260812-repository-doctor-contract`).
- The official asset architecture separately requires the canonical Doctor check set to remain unchanged and uses the ready result as the delivery-agent dispatch gate (`ADR-260812-official-asset-distribution-installation`; `CORE-COMPONENT-260812-official-asset-installation-contract`). Whether AC-10 changes the semantics of an existing check or the vocabulary/schema is explicitly unresolved for Plan; Research selects neither.
- Doctor must remain repository-scoped and must not select issues, inspect issue state, invoke issue ports, or mutate Runner ownership. Existing safe-probe rules restrict filesystem probes to exclusive randomized resources under validated repository-contained ancestors and require cleanup uncertainty to fail.
- External commands must remain typed executable/argument arrays with `shell: false`, an allowlisted environment, bounded execution, redacted diagnostics, and no credential persistence. Current Doctor and Runner command result types are distinct and expose different byte-level facts.
- A functional readiness observation cannot weaken existing tmux ownership rules. Ambient/default servers and unknown sessions, windows, panes, processes, or sockets cannot be inspected, adopted, signaled, or removed as probe resources.
- The accepted tmux identity contract requires original-byte parsing; exact HT and optional final LF transport; strict `@` and `%` identifiers; valid UTF-8 nonempty cwd; nonzero-observe absence; and malformed zero-exit observation as unknown. Alternate separators or version-upgrade guidance are unsupported (`ADR-260814-tmux-identity-failure-recovery`; `CORE-COMPONENT-260814-tmux-identity-diagnostics`).
- Runner relies on one shared repository tmux session in normal operation and uses 15-second adapter bounds. Doctor has independent 2-second-per-command and 9-second-total bounds. Reusing normal Runner behavior cannot silently change either timing contract or contact the normal server.
- Success and every failure boundary named by AC-10 must leave no probe-owned session, window, pane, child process, server process, socket, or temporary file. The current aggregate timer and client timeout do not provide cancellation or server-cleanup proof by themselves.
- Human and JSON meaning must continue to derive from one typed result. Current failure structure is limited to `message` and `remediation`; exposing any additional machine fields would intersect the fixed schema and fixture/documentation contracts.
- Core logic remains strict TypeScript on Node.js 22+ with external systems behind injectable adapters. Repository fixtures are credential-free and deterministic; external Sparkta state, live GitHub, live Copilot, and ambient tmux are excluded.
- Root `justfile` recipes remain validation authority, and both `verify-focused` and `verify` must remain available. The harness delegates and does not replace them.

## Risks and Open Questions

- Plan must decide, without a Research preference, whether the new readiness behavior belongs within an existing check or changes the check vocabulary. The accepted exact 24-ID contract, Doctor fixtures, documentation assertions, and official-asset non-regression rule make that decision architecture-sensitive.
- AC-10 says session/window/pane operations and exact identity/observation formats Runner requires. Runner currently performs the full tmux operation set listed above; the criterion does not specify which operations constitute sufficient readiness proof or whether interactive attach, pane capture, respawn, remain-on-exit, and window removal are all in scope.
- A unique alternate socket can avoid default-server contact according to tmux 3.7b documentation, but uniqueness, stale socket collision, server startup, user/system configuration loading, and proof of final absence remain separate concerns. Repository evidence contains no current isolated-server lifecycle.
- A tmux client may exit or time out while its daemonized server or pane child remains. The current Doctor runner has no server PID or socket ownership fact, and the aggregate `Promise.race` can return before in-flight evaluation settles. Cleanup after client launch failure, malformed output, operation failure, timeout, parse failure, kill failure, or aggregate expiry is therefore unproved today.
- Current production Doctor has only repository-contained token files, not a temporary-directory owner with recursive exact cleanup. The appropriate location and ownership proof for a socket or temporary directory are unresolved and intersect the accepted repository-contained probe restriction.
- The Doctor runner decodes and redacts output but does not retain original bytes. The Runner identity parser requires original bytes. How Doctor can prove the exact byte transport without weakening redaction, bounds, or adapter layering is unresolved for Plan.
- Current redaction is pattern-based and preserves most non-secret text, including paths and tmux field values. AC-10 asks for structured actionable failure evidence but does not define its fields, caps, or whether temporary socket/session details may appear. Current schema has only message/remediation strings.
- The live Doctor runner truncates only after buffering complete output. A malformed or hostile tmux executable could emit unbounded output before the command deadline; current repository proof does not establish an in-memory output cap.
- Isolated socket selection does not by itself isolate tmux startup configuration. The tmux 3.7b manual says system and user configuration load when a server starts; Doctor passes HOME and XDG_CONFIG_HOME. Whether readiness should reflect or bypass those ambient configuration effects is not specified.
- Current built Doctor fixtures can report READY with a no-op tmux executable. There is no current credential-free proof for nonfunctional tmux, malformed create/observe bytes, cleanup failure, residual process/socket detection, or success/failure cleanup parity.
- Updating Doctor semantics would make the executable-only table row, safe-observation narrative, troubleshooting, manifests, exact-order assertions, and ready fixture stale. No new configuration field, network API, database, service, container, or deployment mechanism is stated by AC-10, but schema/check-count and operator-documentation migration impact depend on the unresolved Plan decision.
- No Research-stage blocker prevents handoff. The unresolved items above are Plan decisions and proof gaps, not permission to access Sparkta or ambient tmux.
