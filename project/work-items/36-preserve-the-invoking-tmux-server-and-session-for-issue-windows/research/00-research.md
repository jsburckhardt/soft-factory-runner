# Research Brief: Preserve the invoking tmux server and session for issue windows

## GitHub Issue
- **Issue:** #36
- **Title:** Preserve the invoking tmux server and session for issue windows
- **Work Item:** project/work-items/36-preserve-the-invoking-tmux-server-and-session-for-issue-windows

## Scope Classification
- **Scope Type:** issue

## Problem Statement
Soft Factory Runner currently addresses tmux through its default target even when invoked by a client attached to another server. The invoking tmux context is not available to Runner tmux subprocesses, and generated session/window names alone cannot distinguish servers. In custom-socket environments, including Sparkta devcontainers, an issue run can therefore create a window in a server the invoking user cannot see.

Runner must create and manage its own issue window in the invoking server and current session when invoked from a valid tmux client. Outside tmux it must retain deterministic standalone behavior. The selected target must remain exact throughout later lifecycle commands without extending ownership to arbitrary pre-existing windows.

## Acceptance Criteria

**Core**
- [ ] From a valid client on a non-default socket, one run creates one Runner-owned issue window in that clients current server and session; a bounded local query through the same socket/session returns its exact window and pane, and no same-run window exists on the default server.
- [ ] Outside tmux, a run selects the documented standalone target deterministically: two sequential clean runs for the same repository resolve the same server/session naming behavior, while runs for two differently named repositories resolve distinct session targets.
- [ ] The selected server/socket, session, window, and pane identity is persisted, and reconciliation authorizes a lifecycle action only when the observed target matches that complete identity.
- [ ] Status, reconcile, resume, attach, logs, stop, and cleanup use only the persisted exact target when invoked from the original session, another tmux context, or outside tmux; for each invocation context, human and JSON results agree whether that target matched, was absent, or mismatched.
- [ ] Cleanup removes only the exactly owned issue window, attach selects only its exact window and pane, logs contain only its transcript, and status does not change either the selected or an unrelated tmux inventory.
- [ ] Target selection never adopts, repurposes, or infers ownership of an arbitrary pre-existing window, including one with the expected name.

**Edge Cases**
- [ ] With two isolated servers containing identical session and window names, each persisted run is observed and controlled only on its own server; after one run is stopped and cleaned, its exact issue window is absent and the other servers complete inventory is unchanged.
- [ ] A finite matrix containing malformed invoking evidence, evidence for a stopped server, nested or contradictory evidence naming more than one credible target, and evidence that cannot resolve to exactly one current session exits nonzero with a machine-readable refusal before tmux mutation; the run-state inventory and every isolated server inventory are byte-for-byte unchanged in each row.
- [ ] Absence of invoking evidence is treated only as outside-tmux fallback, not as permission to use an arbitrary existing server; an existing expected-name window in the fallback target is preserved and refused rather than adopted.
- [ ] Two simultaneous starts for one issue produce exactly one owner and one issue window; one bounded overlap of cleanup with status and one with reconciliation each reports either the complete pre-cleanup target or its complete absence, without mixed target identities or mutation outside the owned server/session.
- [ ] Repeating stop or cleanup after the owned target is absent reports the same terminal or absent outcome without tmux mutation; attach, logs, and resume with an absent or mismatched target exit nonzero without tmux mutation.
- [ ] Sentinel values placed in malformed invoking evidence and unrelated inherited environment entries are absent from human output, JSON output, snapshots, events, diagnostics, and retained logs; the raw invoking-context tuple and its server process identifier are not retained or rendered.

**Verification**
- [ ] Doctor/readiness evidence distinguishes valid in-tmux targeting, outside-tmux fallback, and every invalid-context matrix row through bounded checks whose before/after inventories prove that ambient and unrelated tmux resources are unchanged.
- [ ] Repeatable repository-local evidence uses isolated sockets and sessions plus machine-observable inventories to prove custom-socket visibility, fallback determinism, persisted lifecycle consistency, collision isolation, finite refusals, repeated/concurrent outcomes, and cleanup that removes the exact owned window while leaving all unrelated inventory unchanged, without credentials or network access.
- [ ] User documentation explains in-tmux behavior, standalone fallback, lifecycle behavior across later invocation contexts, invalid/stale target outcomes, the raw-value confidentiality boundary, and non-adoption of arbitrary windows.
- [ ] The focused and full repository verification commands pass with inspectable evidence mapped to these criteria.

## Constraints

- Preserve the issue acceptance criteria exactly as fetched; later stages must retain their ordering and the stable work-item directory name.
- Preserve all eight intentional `.agents/skills/` deletions. They are in scope for eventual commit and must not be restored. The four stale `skills-lock.json` entries are live references that remain to be removed or updated outside Research.
- Existing tmux ownership rules prohibit adopting or repurposing a pre-existing same-name resource. Unknown, malformed, absent-without-recorded-progress, mismatched, or ambiguous resources cannot authorize launch, attach, signaling, restart, log capture, or cleanup.
- Existing lifecycle policy requires one shared reconciliation report, one bounded observation per boundary, no polling or hidden retry, stable typed refusal codes, nonzero operational refusals, and equivalent human/JSON meaning.
- New-run ownership remains atomic per issue and subject to an atomic repository concurrency lease before downstream tmux creation. Distinct runs must retain distinct owned windows and panes.
- Durable state must remain versioned and atomic; transition events remain append-only and are written before snapshot replacement. Persisted facts and runtime observations remain separate, and event replay requires a contiguous identity-matching chain.
- Tmux create/observe parsing remains original-byte, strict, LF-terminated, and identical between normal and Doctor paths. Malformed zero-exit output remains unknown; nonzero target observation currently means absence. Diagnostic structure is bounded and value-free.
- Confidentiality contracts prohibit credentials, raw tmux output, cwd/path components, command/environment/field values, identifiers, hashes, raw bytes, and other-run values in durable or rendered diagnostics. Issue #36 additionally forbids retention or rendering of the raw invoking-context tuple and server process identifier.
- Subprocesses use executable/argument arrays, `shell: false`, validated inputs, bounded execution, environment allowlists, and redacted typed results. Current strict configuration rejects undeclared fields.
- Attach, logs, stop, resume, status/reconcile, and cleanup must continue to use shared persisted ownership and observed identity rather than ambient command context as authority. Explicit cleanup remains ordered and progress-recorded; automatic merged cleanup retains tmux.
- Product Doctor must retain its ordered 24 blocking check IDs, bounded aggregate deadline, isolated private socket/configuration, value-free evidence, unconditional exact cleanup, and separation from ambient harness Doctor. It cannot contact or mutate unrelated ambient tmux resources.
- Root `justfile` recipes remain command authority; package/runtime constraints remain Node.js 22+, strict TypeScript, shell-free local CLI operation, and deterministic repository-local verification without credentials or network access.

## Risks and Open Questions

- The repository has no current typed model or documented grammar for invoking-context evidence. Malformed, stale-server, nested, contradictory, and multiple-credible-target cases therefore have no existing classification boundary to reuse directly.
- Server-local window/pane IDs can be identical across isolated servers. Persisting only the current `TmuxIdentity` can report a false match and direct capture, attach, stop lineage, or cleanup to the wrong server when names and IDs collide.
- The current standalone behavior depends on tmux's implicit default server. Its server naming/selection is not persisted or documented, and normalized repository names can collide after lowercasing and punctuation collapse.
- Current later commands discard ambient `TMUX` values and also lack a persisted selector, so invocation from the original session, another server, or outside tmux cannot presently converge on one exact non-default target.
- `attach-session` is currently bare and follows `select-window`/`select-pane`; invocation from an already attached or nested tmux client may have context-dependent behavior that current repository evidence does not classify.
- Same-issue lock admission prevents duplicate starts, but current status/reconciliation observation and explicit cleanup operate in separate bounded steps. Repository evidence does not establish that overlap can never expose a mixed tmux identity when a window disappears between observation, capture, and removal.
- Doctor's strong private-socket isolation intentionally avoids ambient context. Extending readiness meaning for Issue #36 is constrained by the fixed 24-ID vocabulary and by the prohibition on exposing probe/context values.
- Sentinel confidentiality is well defined for existing tmux identity diagnostics and Copilot configuration, but no current persistence/rendering path exists for invoking evidence. Every future boundary that handles such evidence will need to remain consistent with the stronger raw-tuple and server-PID prohibition in the issue.
- Existing controlled tmux tests validate command formatting and parser behavior but do not prove real multi-server custom-socket selection. Live adapter coverage is excluded, so current repository evidence cannot establish custom-socket visibility or cross-server inventory isolation.
- The four stale `skills-lock.json` references conflict with the intentional deletion state until a later stage updates them; leaving them live would violate the user's required final deleted-reference inventory.
- Research tooling friction was concrete: `rg` was unavailable, so repository-wide reference searches were repeated with `git grep`, recursive `grep`, and symlink enumeration. The missing `python` alias also caused one artifact-write retry using `python3`. These were captured as harness observations `DL-001`, `DL-002`, and `CONF-001` for agent `rpiv-research`.
